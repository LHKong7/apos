## 一、产品概述

### 1.1 产品名称

Autonomous Project OS

中文暂定名：

自主项目操作系统

简称：

APOS

---

### 1.2 产品定位

Autonomous Project OS 是一款面向 Human–Agent 混合团队的自主项目管理与交付平台。

用户通过自然语言、表单、文档或外部系统录入需求后，系统中的 Project Agent 可以自动完成：

- 需求理解与澄清；
- 项目规划；
- 任务拆解；
- 依赖分析；
- 人员与 Agent 分配；
- 多 Agent 协同执行；
- 项目进度跟踪；
- 风险和阻塞识别；
- 交付物验证；
- 项目知识沉淀。

系统不会让 Agent 无限制地自主执行，而是通过 Policy Engine 和 Human-in-the-Loop 机制，在需求目标、方案选择、高风险操作、生产发布和业务验收等关键阶段引入人类决策。

一句话定义：

> 让 Agent 负责项目的持续推进，让人类在目标、风险和责任边界上保持控制。

## 二、产品背景

传统项目管理工具主要解决以下问题：

- 记录需求；
- 创建任务；
- 分配负责人；
- 展示项目进度；
- 提醒任务延期；
- 统计完成情况。

这类产品的基本假设是：

> 人是任务的主要执行者，系统只是记录和展示工具。

随着 Code Agent、Research Agent、Test Agent、Browser Agent、Data Agent 等智能体进入企业，项目团队将逐渐变成：

```
Human
   +
Project Agent
   +
Code Agent
   +
Test Agent
   +
Review Agent
   +
Research Agent
```

此时，传统项目管理工具面临几个问题：

1. Agent 无法作为正式执行主体进入项目管理体系；
2. 看板只能记录状态，无法主动推动项目；
3. Agent 的任务、运行过程和产物缺少统一管理；
4. 多个 Agent 之间缺少统一调度和依赖管理；
5. 人类无法清晰知道何时需要介入；
6. Agent 的权限、成本、风险和责任边界缺乏治理；
7. 项目结束后，执行经验难以沉淀为可复用资产。

Autonomous Project OS 的目标不是为传统看板增加一个聊天机器人，而是重新设计一套适合 Human–Agent 混合团队的项目运行系统。

---

## 三、产品愿景

### 3.1 Vision

构建企业内部的人机协同项目操作系统，让项目能够在明确的人类治理边界内自主规划、自主推进、自主恢复并持续学习。

---

### 3.2 产品核心理念

#### Agent 推进，人类治理

Agent 负责高频、重复、可验证的执行工作，人类负责：

- 定义目标；
- 判断价值；
- 确认关键约束；
- 处理高风险决策；
- 承担最终责任；
- 验收业务结果；
- 制定和优化规则。

#### Flow 优先，而不是任务数量优先

系统不只关心完成了多少任务，还需要持续观察：

- 工作是否顺畅流动；
- 哪个阶段形成瓶颈；
- 哪些任务等待时间过长；
- 哪些 Agent 持续失败；
- 哪些决策长期无人处理；
- 哪些环节返工率过高；
- 项目是否正在偏离目标。

#### Policy 驱动，而不是每一步都审批

Human-in-the-Loop 不等于让人逐条确认 Agent 的所有操作。

系统根据任务风险、权限、成本、置信度和业务影响，动态决定：

- 自动执行；
- 执行后通知；
- Agent 交叉审核；
- 人类抽样审核；
- 人类强制审批；
- 多人会签；
- 人工接管。

#### 所有行为可追溯

每次计划、分配、执行、修改、审批和发布，都需要留下完整记录。

系统需要回答：

- 谁做了什么；
- 为什么这样做；
- 使用了哪些上下文；
- 调用了哪些工具；
- 产生了哪些结果；
- 谁批准了关键决策；
- 失败后如何恢复；
- 最终交付是否达成目标。

## 四、目标用户

### 4.1 企业研发团队

适用于存在产品、研发、测试、运维、安全等角色的研发组织。

主要诉求：

- 自动拆解和分配研发任务；
- 对接内部研发 Agent；
- 管理多人和多 Agent 协作；
- 控制生产发布和数据权限；
- 识别项目风险和交付瓶颈；
- 降低项目经理的协调成本。

---

### 4.2 OPC 与一人公司

适用于主要由一名创始人或少量核心成员运营的公司。

主要诉求：

- 一个人管理多个项目；
- 通过多个 Agent 承担产品、研发、测试、调研和运营工作；
- 减少人工更新任务和催进度；
- 快速完成从想法到交付的全过程；
- 在关键决策上保持控制。

---

### 4.3 小型创业团队

适用于人员少、迭代快、角色边界模糊的团队。

主要诉求：

- 快速创建项目；
- 自动形成执行计划；
- 将任务动态分配给人或 Agent；
- 降低项目管理工具的配置成本；
- 避免复杂 Jira 流程带来的管理负担。

---

### 4.4 企业项目管理者

包括项目经理、产品负责人、技术负责人和业务负责人。

主要诉求：

- 查看项目健康度；
- 处理需要人类参与的关键决策；
- 及时识别延期、阻塞和成本异常；
- 了解 Agent 正在做什么；
- 对高风险操作保持控制。

---

## 五、核心使用流程

Autonomous Project OS 的完整项目生命周期如下：

```
需求进入
   ↓
AI 分析与澄清
   ↓
人类确认需求目标
   ↓
AI 生成项目计划
   ↓
人类确认关键方案与约束
   ↓
任务拆解与资源分配
   ↓
Human / Agent 混合执行
   ↓
持续监控与异常恢复
   ↓
自动测试与多层评审
   ↓
人类确认高风险交付
   ↓
发布与业务验收
   ↓
经验沉淀与策略优化
```

建议系统使用六个主要项目阶段：

```
Intake
Planning
Execution
Review
Release
Done
```

Human Gate 通过卡片状态、决策任务和审批标识体现，而不是全部展开为独立看板列。

- 业务负责人；
- 技术负责人；

- 项目 Agent；
- 时间范围；
- 预算；

- 关联代码仓库；

- 工作拆解结构；
- 执行阶段；
- 依赖图；
- 关键路径；
- Agent 分配建议；

- 发布方案；

---

### 6.7 Decision

包含：

- 决策问题；
- 触发原因；
- 推荐方案；
- 备选方案；
- 影响分析；
- 风险等级；
- 相关证据；
- 决策责任人；
- 决策时限；
- 决策结果；
- 附加约束；
- 审批记录。

---

### 6.8 Artifact

项目执行过程中产生的交付物。

例如：

- 代码；
- Pull Request；
- 测试报告；
- 产品文档；
- 技术方案；
- 数据分析；
- 页面截图；
- 部署记录；
- 发布说明；
- 会议纪要。

---

### 6.9 Event

系统内所有行为统一记录为事件。

例如：

- 需求创建；
- 计划生成；
- 任务分配；
- Agent 启动；
- 工具调用；
- 执行失败；
- 人类审批；
- 状态变化；
- 代码提交；
- 发布完成；
- 业务验收。

Event 是项目可追溯、可回放和可审计的基础。

---

### 6.10 Policy

定义项目中的自动化边界。

例如：

```
涉及生产数据库修改
→ 必须由 DBA 审批

低风险文案调整
+ 自动测试通过
+ 成本低于阈值
→ 自动批准
```

## 八、核心功能设计

### 8.1 Home 工作台

用户登录后进入个人工作台。

工作台需要根据用户角色展示不同内容。

#### 管理者视角

展示：

- 项目健康度；
- 高风险项目；
- 延期预测；
- 等待人类处理的决策；
- Agent 成本趋势；
- 团队负载；
- 项目交付情况。

#### 项目负责人视角

展示：

- 当前项目状态；
- 关键路径；
- 阻塞任务；
- 待批准计划；
- 待处理异常；
- Agent 工作进度；
- 即将到期里程碑。

#### 开发者视角

展示：

- 分配给自己的任务；
- Agent 已完成、等待 Review 的任务；
- 需要人工接管的任务；
- 相关代码和上下文；
- 今日需要处理的决策。

#### OPC 视角

展示：

- 所有项目总览；
- Agent 当前工作；
- 需要本人处理的事项；
- 今日预计交付；
- 成本消耗；
- 项目风险。

---

### 8.2 Requirement Center 需求中心

#### 8.2.1 多渠道需求录入

支持通过以下方式创建需求：

- 手动填写；
- 自然语言对话；
- 上传 PRD 或文档；
- 从会议纪要提取；
- 从邮件提取；
- 从客户反馈导入；
- 从 Jira、Plane、Linear 等系统同步；
- 通过 API 或 Webhook 创建。

#### 8.2.2 AI 需求结构化

Agent 自动将原始描述转换为：

- 需求标题；
- 业务背景；
- 用户问题；
- 业务目标；
- 用户故事；
- 功能范围；
- 非功能要求；
- 验收标准；
- 潜在风险；
- 依赖关系；
- 需要澄清的问题。

#### 8.2.3 需求完整度检查

系统对需求进行评分：

- 目标完整度；
- 范围清晰度；
- 验收标准完整度；
- 依赖明确度；
- 风险识别程度；
- 技术上下文完整度。

#### 8.2.4 AI 澄清

Agent 自动提出关键澄清问题。

问题按照影响程度分类：

- 可自动从知识库解决；
- 可根据默认规则处理；
- 可记录假设后继续；
- 必须由人类确认。

#### 8.2.5 Human Gate：需求确认

人类可以：

- 批准需求；
- 修改后批准；
- 补充说明；
- 要求重新分析；
- 驳回；
- 暂缓；
- 委派其他人确认。

只有完成需求确认，项目才能正式进入 Planning 阶段。

---

### 8.3 Project Agent 项目智能体

Project Agent 是项目级的管理与调度智能体。

#### 8.3.1 项目规划

根据需求和组织上下文，自动生成：

- 项目范围；
- 阶段划分；
- 任务拆解；
- 工作量预估；
- 技术方案建议；
- Agent 与人员需求；
- 依赖关系；
- 关键路径；
- 时间计划；
- 风险清单；
- 里程碑；
- 预算预估。

#### 8.3.2 动态任务拆解

Project Agent 可以将需求拆分为多层 Work Item：

```
Requirement
├── Research
├── Design
├── Backend
│   ├── API
│   ├── Database
│   └── Unit Test
├── Frontend
│   ├── UI
│   └── Integration
├── Test
├── Review
└── Release
```

任务拆解不应只发生一次。

当执行过程中发现新问题时，Project Agent 可以：

- 创建补充任务；
- 拆分复杂任务；
- 合并重复任务；
- 调整依赖；
- 修改优先级；
- 更新计划。

#### 8.3.3 执行图生成

Project Agent 将任务关系生成 Execution Graph。

节点可以是：

- 人类任务；
- Agent 任务；
- 审批节点；
- 自动化节点；
- 等待节点；
- 验证节点；
- 发布节点。

边表示：

- 前置依赖；
- 数据依赖；
- 审批依赖；
- 触发关系；
- 重试关系；
- 回退关系。

#### 8.3.4 智能调度

Project Agent 根据以下条件分配任务：

- Agent 能力；
- Skill 匹配；
- 历史成功率；
- 当前负载；
- 上下文匹配度；
- 权限范围；
- 模型成本；
- 任务时限；
- 风险等级；
- 是否需要人类经验。

任务可以分配给：

- 单个人类；
- 单个 Agent；
- 多个 Agent 并行执行；
- Agent 执行、人类审核；
- 人类执行、Agent 辅助；
- Agent 集群；
- 外部服务。

#### 8.3.5 进度维护

Project Agent 自动读取 Agent Run、代码仓库、测试系统和外部项目系统的状态，更新任务进度。

用户不需要手动拖动大部分卡片。

系统需要明确区分：

- 系统自动更新；
- Agent 更新；
- 人类更新；
- 外部系统同步。

#### 8.3.6 项目摘要

Project Agent 可自动生成：

- 每日项目摘要；
- 周报；
- 里程碑报告；
- 风险报告；

### 8.8 Human-in-the-Loop 机制

Human-in-the-Loop 贯穿项目全生命周期。

#### 8.8.1 需求阶段

Agent 负责：

- 结构化需求；
- 补充上下文；
- 提出问题；
- 生成验收标准。

人类负责：

- 确认目标；
- 判断业务价值；
- 确认优先级；
- 确认关键业务规则。

#### 8.8.2 规划阶段

Agent 负责：

- 拆解任务；
- 生成依赖；
- 估算时间和成本；
- 推荐执行者。

人类负责：

- 确认范围；
- 确认关键方案；
- 确认交付承诺；
- 确认高风险路径。

#### 8.8.3 调度阶段

默认由 Agent 自动分配。

以下情况需要人类确认：

- 使用高成本模型；
- 占用关键人员；
- 跨团队协作；
- 使用敏感资源；
- Agent 能力不足；
- 成本超出预算。

#### 8.8.4 执行阶段

Agent 默认自主执行。

以下情况触发人类介入：

- 连续失败超过阈值；
- 与计划明显偏离；
- 发现需求冲突；
- 涉及不可逆操作；
- 多 Agent 结论冲突；
- 需要超出权限的操作；
- 成本异常增长；
- 任务长期阻塞。

#### 8.8.5 Review 阶段

根据风险分级。

低风险任务

```
Agent 执行
→ 自动验证
→ Review Agent
→ 自动通过
```

中风险任务

```
Agent 执行
→ 自动测试
→ Review Agent
→ 人类抽样或快速确认
```

高风险任务

```
Agent 执行
→ 多 Agent 交叉审核
→ 完整测试
→ 指定人类强制审核
```

#### 8.8.6 Release 阶段

- 开发环境：允许 Agent 自动发布；
- 测试环境：允许自动发布并通知；
- 预生产环境：按风险策略处理；
- 生产环境：默认需要审批或满足企业自动发布策略。

#### 8.8.7 验收阶段

Agent 负责验证技术结果。

人类负责判断：

- 是否满足业务目标；
- 是否符合真实使用场景；
- 是否可以正式结项；
- 是否需要继续优化。

#### 8.8.8 Learning 阶段

Agent 自动生成：

- 项目复盘；
- 瓶颈分析；
- Agent 表现；
- 决策总结；
- Skill 候选；
- Policy 候选。

人类确认哪些经验可以进入组织知识库和默认规则。

#### 8.9.3 Policy 示例

```

```

```

```

```
暂停任务并请求技术负责人处理
```

#### 8.9.4 自治等级

每个项目可以选择：

**Human-led**

Agent 提建议，人类做主要决定。

适用于：

- 高风险项目；
- 新业务；
- Agent 能力尚未验证；
- 强监管场景。

**Agent-led with Approval**

Agent 自主规划和执行，关键节点由人类批准。

这是默认模式。

**Agent-autonomous**

Agent 自主规划、执行和验证，仅在异常时请求人类。

适用于：

- 低风险任务；
- 重复性任务；
- 测试或沙箱环境；
- 已验证的成熟流程。

- 审批记录；
- 执行结果；
- 失败原因；
- 关联项目和任务。

## 十一、通知与升级机制

系统通知应围绕"需要行动"设计，而不是发送大量 Agent 日志。

### 通知类型

- 需要决策；
- 决策即将超时；
- 项目风险升高；
- Agent 连续失败；
- 任务长期阻塞；
- 成本即将超限；
- 关键里程碑完成；
- 发布异常；
- 人工接管请求；
- 业务验收请求。

### 升级规则

例如：

```
决策等待 4 小时
→ 提醒责任人

等待 8 小时
→ 提醒项目负责人

等待 24 小时
→ 提醒上级并暂停关键路径
```

## 十二、MVP 产品范围

第一版不建议立即实现完整 Autonomous Project OS，而应验证最核心闭环。

### 12.1 MVP 核心目标

验证以下假设：

> 用户录入一个需求后，Project Agent 能够将其转化为可执行计划，分配给人或 Agent，并在关键节点请求人类决策，最终推动需求完成。

## 十五、关键产品差异

### 对比传统 Kanban

传统 Kanban：

- 用户创建任务；
- 用户分配任务；
- 用户更新状态；
- 用户发现阻塞；
- 用户推动流程。

Autonomous Project OS：

- Agent 理解需求；
- Agent 生成计划；
- Agent 分配任务；
- Agent 执行任务；
- 系统自动更新状态；
- Agent 识别和恢复阻塞；
- 人类只处理关键决策。

### 对比 Jira + AI 助手

Jira + AI 助手主要是：

> AI 帮助用户更快使用 Jira。

Autonomous Project OS 是：

> Agent 本身成为项目执行者和协调者，系统围绕 Agent 的运行、治理和协作重新设计。

### 对比单个 Code Agent

单个 Code Agent 主要解决：

> 如何完成一个研发任务。

Autonomous Project OS 解决：

> 如何将业务需求持续转化为一组可治理、可追踪、可协同的 Human–Agent 执行流程。

## 十八、产品边界

Autonomous Project OS 不负责取代所有专业工具。

它不需要重新实现：

- 代码托管；
- CI/CD；
- 文档编辑器；
- 企业聊天；
- 数据仓库；
- 完整 ERP；
- 完整 CRM。

它的核心角色是：

> 连接项目目标、人员、Agent、工具、知识与决策，并持续驱动项目 Flow。

因此，它更像企业项目的控制面和运行时，而不是所有执行能力的集合。

## 十九、产品总结

Autonomous Project OS 不是一个增加了 AI 功能的传统看板，也不是一个单纯负责自动拆任务的项目管理助手。

它是一套面向 Human–Agent 混合团队的项目运行系统。

在这套系统中：

- Requirement 定义需要实现的业务价值；
- Project Agent 负责规划和持续推进；
- Human 与 Agent 共同成为执行主体；
- Flow Engine 管理真实的项目流动；
- Policy Engine 定义 Agent 的自治边界；
- Human Decision Center 承接关键决策；
- Agent Workspace 管理智能体执行过程；
- Knowledge Center 将项目经验沉淀为组织资产；
- Delivery Analytics 持续发现和优化交付瓶颈。

产品最终希望实现的，不是让人类退出项目，而是重新分配人类与 Agent 的职责：

```
Agent：
规划、拆解、分配、执行、监控、重试、同步、总结

Human：
定义目标、判断价值、控制风险、处理例外、承担责任、验收结果
```

Autonomous Project OS 的核心价值可以总结为：

> 让项目能够自主向前流动，同时确保人类始终掌握目标、风险与最终决策权。
