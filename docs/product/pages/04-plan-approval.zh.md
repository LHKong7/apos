## 2. 页面目标

让人类在**两分钟内**判断一份 AI 生成的执行计划是否可以放行，并且清楚知道自己批准的是什么。

页面要回答：

1. Agent 打算怎么干？分几步、谁来做？
2. 要多久、花多少钱？
3. 哪里最可能出问题？
4. 我批准之后，哪些事情会在没有我参与的情况下自动发生？

**最后一条是本页的灵魂。** 批准计划 = 批准一批自动化行为，用户必须清楚看到自己让渡了什么。

**入口**：需求确认后自动进入；项目总览「计划待批准」横幅；决策中心的计划批准类决策；项目内 Tab「计划」。

**出口**：

| 操作 | 去向 |
| --- | --- |
| 批准计划 | `05 Autonomous Board`（任务开始流动） |
| 要求修改 | 停留，Agent 重新规划 |
| 手动调整后批准 | `05 Autonomous Board` |

| 查看依赖全貌 | `07 Execution Graph` |
| 驳回 | 返回 `03 需求录入` |

## 5. 区域详解

### 5.1 计划元信息

生成时间、耗时、成本、使用模型、版本号。计划有版本（v1 / v2 / v3），支持**版本对比**——当 Agent 重新规划后，用户需要看到"改了什么"而不是从头再读一遍。

版本对比视图：新增任务绿色、删除任务红色删除线、变更字段黄色高亮。

### 5.2 五个概览指标

| 指标 | 内容 | 关注点 |
| --- | --- | --- |
| 任务 | 总数 + 人机拆分 | 一眼看出自动化比例 |
| 工期 | 总天数 + 是否满足期望截止时间 | 超期时红色并显示差值 |
| 成本预估 | 总额 + 占预算比例 | 超预算时阻断批准，需先调预算 |
| 人类参与 | 节点总数 + 归我的数量 | 让用户知道自己要投入多少 |
| 风险 | 等级 + 项数 | 高风险项数量突出显示 |

### 5.3 「批准后将自动发生」（本页核心）

这是把 Policy Engine 的抽象规则**翻译成人话**的地方。系统根据当前项目 Policy + 自治等级，计算出批准计划后哪些行为会自动发生，用自然语言列出。

必须包含：
- 会自动执行多少任务、涉及哪些系统（代码库、数据库、部署环境）
- 会自动产生哪些不可逆或外部可见的效果（合并代码、部署、发通知）
- 预计花多少钱
- **反向清单**：哪些事情仍会来找你——这同样重要，用户需要知道安全网在哪

「逐条查看」展开为规则明细，每条标注命中的 Policy ID，可直接跳 `13 Policy 配置` 调整。

如果项目是 `Agent-autonomous`，本区域用橙色边框强调，因为让渡的权限更大。

### 5.4 任务拆解（文档 8.3.2）

多层树形，默认展开到第二层。每个任务行显示：

| 元素 | 说明 |
| --- | --- |
| 阶段图标 + 任务名 | 按 Research / Design / Backend / Frontend / Test / Review / Release 分组 |
| 执行主体 | Assignee Chip（§5.2），Agent 与人类视觉区分 |
| 工期 | 预估小时/天 |
| 成本 | Agent 任务显示预估成本，人类任务不显示 |
| 风险标记 | 高及以上显示，附风险说明与所需管控 |
| 人类节点标记 | 👤 图标，说明该节点需要谁在什么时候介入 |

**行内操作**（无需进详情页即可调整）：改派执行主体、调整工期、拆分任务、删除、追加人类审核节点。

任何手工调整都会：
1. 标记该任务为 `👤 已人工调整`
2. 重算受影响的下游工期与关键路径
3. 若调整造成依赖冲突，立即在行下方红字提示

**改派下拉**要显示候选 Agent 的匹配依据（文档 8.3.4）：

```
改派为：
 [🤖 code-agent-1]  匹配度 92%  成功率 92%  负载 2/5   ~$6.4   ← 当前
 [🤖 code-agent-2]  匹配度 78%  成功率 96%  负载 0/5   ~$9.1
 [👤 张伟]          领域匹配    当前负载 3 项
 ─────────────
 说明：匹配基于 Skill(SQL优化, TypeScript) 与历史同类任务成功率
```

### 5.5 时间线视图

甘特形式，标注关键路径（红色）、里程碑（菱形）、人类参与节点（👤 图标）、缓冲区。

横轴顶部标出需求的期望截止时间，超出部分用红色斜纹区表示——**让"来不及"这件事视觉上无法忽略**。

### 5.6 依赖图视图

嵌入 `07 Execution Graph` 的只读简化版，用于批准前快速核对依赖是否合理。提供「在执行图中打开」跳转完整版。

### 5.7 风险视图（文档 6.6 风险清单）

每条风险：描述、等级、可能影响、Agent 建议的缓解措施、是否已在计划中安排对应任务。

用户可以：接受风险（记入 `已接受风险`，进项目记忆）、要求增加缓解任务、提高该任务的审批等级。

### 5.8 里程碑视图

里程碑名称、日期、包含任务、验收方式、责任人。里程碑会成为后续通知与报告的锚点（文档十一）。

### 5.9 假设提示区

从 `03 需求录入` 带过来的未经二次确认的假设。放在批准按钮上方——**这是最后一次纠正需求理解错误的机会，成本远低于执行后返工。**

### 5.10 修改意见与操作

「要求修改」时，用户的自然语言意见会连同当前计划一起给 Project Agent 重新规划，生成 v2。按钮上显示重规划成本预估。

「批准并开始执行」前的二次确认框：

```
批准后将立即：
· 调度 3 个任务开始执行（research-agent、code-agent-1）
· 预计今日消耗 ~$8

☑ 有任务失败或需要决策时通知我

              [再看看]  [确认批准]
```

## 6. 核心交互流程

**快速批准（信任度高时）**

```
进入 → 看 5 个指标 → 看"批准后将自动发生" → [批准] → 看板
（目标 < 60 秒）
```

**审慎批准（高风险项目）**

```
进入 → 展开任务树 → 检查高风险任务的管控措施
     → 切时间线确认关键路径合理
     → 给"数据库索引变更"追加人类审核节点
     → 调整某任务改派给成本更低的 Agent
     → [批准]
```

**要求修改**

```
写下意见「前端不用等后端，可以并行」→ [要求修改]
→ Agent 重新规划（1–3 min）→ 生成 v2
→ 自动进入版本对比视图，高亮改动 → [批准]
```

## 7. 状态设计

| 状态 | 处理 |
| --- | --- |
| 规划中 | 全页展示进度：「正在拆解任务 (12/18)…」+ 当前步骤说明，可取消 |
| 规划失败 | 显示原因（如上下文不足、超时），提供 [重试] [回到需求页补充信息] [手动创建计划] |
| 已批准（只读） | 头部显示批准人、时间、批准时的假设快照；提供 [基于此计划重新规划]（生成新版本） |
| 执行中的计划变更 | 当 Project Agent 在执行期间动态调整计划（文档 8.3.2），生成新版本并进入本页，标题为「计划变更待批准」，默认展示与当前版本的 diff |
| 成本超预算 | 批准按钮置灰，提示「预估成本 $620 超出预算 $500」+ [调整预算] [要求 Agent 降低成本方案] |
| 工期超期望截止 | 不阻断，但需勾选「我知晓将延期 2 天」才能批准 |

## 8. 权限

| 操作 | 要求 |
| --- | --- |
| 查看计划 | 项目成员 |
| 调整任务（改派/工期/拆分） | `pm` / `tech_lead` |
| **批准计划** | `tech_lead`（技术方案）+ `sponsor`（交付承诺）——高风险项目需双签 |
| 要求修改 / 驳回 | `pm` 及以上 |
| 提高预算 | `sponsor`（文档 8.7.5 预算超限 → 项目 Sponsor） |
| 降低某任务的审批等级 | `tech_lead`，记审计 |

**双签规则**：项目风险等级为「高」或计划包含不可逆生产操作时，需要 `tech_lead` 与 `sponsor` 各自批准，页面显示签署进度（`已签 1/2`）。

## 9. 数据依赖

**领域对象**：`Plan`（全字段）、`WorkItem`（草稿态）、`Agent`（候选与匹配度）、`Requirement`（假设与验收标准）、`Policy`（自动化清单计算）、`Decision`（批准记录）

**接口**

```
GET  /api/plans/{id}
     → { plan, work_items[], critical_path[], milestones[], risks[],
         cost_estimate, auto_actions[], required_approvals[] }

GET  /api/plans/{id}/auto-actions
     → [{ description, policy_id, policy_name, reversible, external_visible }]
        ← Policy Engine 预演结果，非硬编码文案

GET  /api/plans/{id}/diff?from=v1&to=v2
PATCH /api/plans/{id}/work-items/{itemId}   { assignee | duration | split | delete }
     → 返回受影响的下游任务与新的关键路径
GET  /api/work-items/{id}/assignee-candidates
     → [{ type, id, name, match_score, match_reasons[], success_rate, load, cost_estimate }]

POST /api/plans/{id}/approve   { note?, acknowledged_overrun? }
POST /api/plans/{id}/revise    { feedback }   → 生成新版本
POST /api/plans/{id}/reject    { reason }
```

## 10. 埋点与指标

| 埋点 | 用途 |
| --- | --- |
| `plan_approval_duration` | 批准耗时（目标中位数 < 90s） |
| `auto_actions_expanded` | **用户是否真的看了自动化清单——治理有效性的关键信号** |
| `plan_item_modified{field}` | AI 规划哪些方面总被人改（改派多 → 调度算法需优化） |
| `plan_revised{round}` | 平均返修轮次（目标 < 1.3） |
| `plan_approved_without_scroll` | 盲批率——过高说明信息组织有问题或用户过度信任 |
| `approval_to_first_failure` | 批准后多久出现第一次失败（计划质量的滞后指标） |

**页面成功标准**：返修轮次 < 1.3；批准后 24h 内因计划本身问题导致的重规划 < 15%。

## 11. 边界与异常

| 情况 | 处理 |
| --- | --- |
| 任务数 > 50 | 默认只展开第一层；提供「只看高风险」「只看我参与的」快捷筛选 |
| 拆解层级 > 4 层 | 提示「拆解过细可能增加调度开销」，允许一键合并末层 |
| 无可用 Agent 匹配某任务 | 该任务标红「无匹配执行者」，默认转人类并在概览指标中计入人类工作量 |
| Agent 全部满载 | 显示排队预估时间，工期自动加上等待时长 |
| 依赖成环 | 阻断批准，明确指出环路 `A → B → C → A`，提供 [让 Agent 修复] [手动断开] |
| 用户手工调整导致关键路径变长 | 实时提示「此调整将使工期 +1.5 天」 |
| 批准时计划已被 Agent 更新 | 拦截批准，提示「计划已更新到 v2」+ 差异对比，需重新确认 |
| 预算未设置 | 成本指标只显示预估值，不做超预算阻断，但提示建议设置预算 |
| 需求在计划生成后被修改 | 计划头部显示「基于的需求已变更」警告 + [重新规划] |

## 12. 待确认问题

1. 「批准后将自动发生」的清单由 Policy Engine 预演生成，需要确认预演的准确性——如果实际执行时命中了未预演到的规则，用户的信任会受损。是否需要在执行阶段对"超出预演范围的自动行为"额外通知？
2. 双签规则的触发条件是否应可配置？不同企业对"高风险"的定义差异很大。
3. 计划版本保留策略：全部保留还是只留最近 N 版？涉及审计要求。
4. 人类任务的工期预估目前由 Agent 给出，准确性存疑。是否应默认留空由人类填写，或提供基于历史 Cycle Time 的建议值？
5. MVP 是否需要「手动创建计划」的兜底路径（Agent 规划失败时）？倾向于需要，但可以做得很简陋。
