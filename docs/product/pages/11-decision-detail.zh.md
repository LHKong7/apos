## 2. 页面目标

给高风险、高影响决策提供**充分但不过载**的判断依据，并把决策结果结构化地传回执行链路。

`10 Decision Center` 的卡片解决 80% 的日常决策；本页服务剩下 20% 需要认真评估的——这些决策往往涉及生产变更、架构选型、预算超支、安全例外。

要回答（比卡片更深一层）：

1. 这个决策的完整背景是什么？之前发生了什么？
2. 每个方案的具体差异、代价和不可逆程度？
3. 有没有类似的历史决策？当时怎么决的？结果如何？
4. 我批准之后，具体会发生什么？
5. 我的约束会如何被执行？

**出口**：

| 操作 | 去向 |
| --- | --- |

## 5. 区域详解

### 5.1 头部与影响横幅

标题、时限状态、风险、可逆性、所属项目、责任人、升级状态。

**影响横幅**用一句话量化后果，是驱动行动的最强信号。内容随时间变化（阻塞时长增长时数字更新）。

### 5.2 为什么需要你决定（文档 8.7.2）

**必须显式展示触发的 Policy 及其条件**，而不是笼统的"需要审批"。理由：

1. 用户理解规则后才能判断规则是否合理，进而优化规则
2. 提供了 [查看规则] 入口——如果用户觉得这类决策不该找他，可以直接去改规则
3. 治理透明度：审计时能追溯到是哪条规则要求了人工介入

同时显示触发时 Agent 正在做什么，附 Run 链接。

### 5.3 背景

Project Agent 生成的决策上下文摘要，包含技术现状、已完成的分析、为什么走到这一步。

**要写给"没有跟进这个项目细节的人"看**——决策责任人（如 DBA）往往不是项目日常成员。

### 5.4 方案对比（核心区域）

表格化并排对比，维度按决策类型动态选择：

| 决策类型 | 对比维度 |
| --- | --- |
| 技术方案 | 耗时、风险、可逆性、成本、长期收益、复杂度 |
| 发布审批 | 影响范围、回滚方案、监控指标、灰度策略、通知计划 |
| 资源/预算 | 成本、周期、质量影响、替代方案 |
| 范围变更 | 工期影响、成本影响、价值、依赖变化 |

**关键设计**：
- 推荐方案在最左侧并标注置信度
- 差异项高亮（相同的值弱化显示）
- **不可逆项用红色标注**——这是最需要人类关注的属性
- 支持"详细"模式展开每个方案的完整说明

### 5.5 Agent 推荐理由

**必须包含不确定性说明**。上例中「置信度 82%：不确定项为生产环境实际 IO 负载」比单纯给个 82% 有用得多——它告诉人类该重点验证什么。

这是把 Agent 从"黑箱推荐器"变成"能说清自己哪里没把握的同事"的关键。

### 5.6 证据（文档 6.7 相关证据）

每份证据：类型、名称、产生者、时间、查看/打开链接。

实时类证据（监控面板）标注为实时并提供直达链接——决策时刻的实时数据往往比几小时前生成的报告更重要。

### 5.7 历史类似决策

系统检索历史决策库，展示：决策内容、当时的选择、**结果如何**。

"结果如何"是最有价值的部分（来自文档 8.12 Knowledge Center 的项目记忆）。人类做决策时最想知道的就是"上次这么干效果怎么样"。

### 5.8 讨论

人与 Agent 混合的讨论区。**Agent 可以被 @ 并回答问题**——上例中张伟问"低峰期是几点"，Agent 立即用监控数据回答。

这是决策效率的重要提升：不需要为了一个数据点去查监控再回来。

### 5.9 决策操作（文档 8.7.3）

底部操作栏。**批准并附加约束**的交互：

```
批准方案 A 并附加约束

附加约束
 ☑ 仅在 02:00–05:00 低峰期执行
 ☑ 执行前创建全量备份
 ☑ 写入延迟超过 30ms 时自动中止并回滚
 ☐ 执行后需人工确认才继续下游任务
 + 自定义约束 [                                        ]

这些约束将：
 · 写入 Work Item「数据库索引变更」的执行约束
 · 传递给执行者（👤 王强）
 · 作为验收检查项

                                      [取消]  [确认批准]
```

**约束必须结构化**（而非自由文本备注），才能被系统实际执行与校验。可选约束由 Agent 根据方案预生成，用户勾选即可——降低填写成本。

### 5.10 会签（多人审批）

需多人批准时显示签署进度、各人状态与意见。

- 已签署者的意见对后续签署者可见（避免独立判断偏差 vs 效率的权衡——这里选效率）
- 出现反对意见时，后续签署者会看到醒目提示
- 全部签署后决策才生效

## 6. 核心交互流程

**认真评估高风险决策**

```
从决策中心进入 → 读影响横幅（阻塞 5 任务）
→ 看"为什么找我"（Policy #7）
→ 方案对比：A 无停机但写入延迟 +8ms，C 长期更优但延期
→ 看 Agent 推荐理由的不确定项：生产 IO 负载
→ 点开实时监控证据确认当前负载
→ 讨论区 @Agent 问低峰期
→ [批准并附加约束] 勾选"低峰期执行"+"自动回滚阈值"
→ 约束写入任务，执行者收到通知
```

**驳回并要求换方案**

```
认为三个方案都不合适 → [要求补充]
→ 填写「需要评估不改索引、改用 ES 的方案」
→ Agent 重新分析并更新决策（生成 v2）
→ 用户收到通知回来重新决策
```

**转交给更合适的人**

```
[转交 ▾] → 选择 李工(资深DBA) → 填说明「涉及分区，请你判断」
→ 原责任人在"已转交"中跟踪
→ 受让人处理后原责任人收到结果通知
```

## 7. 状态设计

| 状态 | 处理 |
| --- | --- |
| 待处理 | 全操作可用 |
| 已超时 | 头部红色 + 显示已升级给谁；操作仍可用（原责任人仍有权处理） |
| 已被他人处理 | 全页只读 + 顶部「李娜已于 14:20 批准方案 A」+ 处理详情 |
| 已处理（回溯查看） | 只读，显示决策结果、约束、执行情况、**结果反馈**（该决策后来效果如何） |
| 会签中 | 显示进度；我已签署则我的操作区变为「已批准，等待其他 2 人」 |
| 关联任务已取消 | 顶部提示 + 决策自动关闭 |
| 方案更新中（要求补充后） | 显示「Agent 正在重新分析…」+ 预计时间 |
| 证据加载失败 | 单项显示失败，不影响其他内容 |

## 8. 权限

| 操作 | 要求 |
| --- | --- |
| 查看 | 项目成员 + 决策相关方 |
| 处理（批准/驳回等） | 该决策的责任人或会签人 |
| 转交 | 责任人本人 / `pm` |
| 参与讨论 | 项目成员 |
| 查看敏感证据（生产数据） | 按数据权限，无权者显示「无权查看」但保留条目 |
| 修改决策时限 | `pm` / `tech_lead` |
| 强制关闭决策 | `pm`，需填原因，记审计 |

**责任不可代行**：非责任人即使是 `org_admin` 也不能直接批准，只能改派责任人（改派本身记审计）。这保证了文档 10.5 要求的"谁批准了关键决策"始终可追溯。

## 9. 数据依赖

**领域对象**：`Decision`（全字段）、`Policy`（触发规则）、`AgentRun`（触发来源）、`WorkItem`、`Artifact`（证据）、`Event`、历史 `Decision`（相似检索）

**接口**

```
GET  /api/decisions/{id}
     → { decision, trigger: { policy, run_id, agent, context },
         background, options: [{ id, name, is_recommended, confidence,
                                 attributes{}, reversible, description }],
         recommendation_rationale, uncertainties[],
         evidence[], similar_decisions[], discussion[], co_signers[],
         impact: { blocked_tasks, critical_path_delay, projected_delay } }

POST /api/decisions/{id}/approve
     ← { option_id, constraints: [{ type, value, enforcement }], note? }
POST /api/decisions/{id}/reject             { reason }
POST /api/decisions/{id}/request-revision   { feedback }
POST /api/decisions/{id}/delegate           { assignee_id, note }
POST /api/decisions/{id}/take-over
POST /api/decisions/{id}/pause-task
POST /api/decisions/{id}/comments           { body, mentions[] }
GET  /api/decisions/{id}/similar            历史相似决策 + 结果
PATCH /api/decisions/{id}/due-at            { due_at, reason }

SSE  /api/stream?channels=decision:{id}
```

**约束的执行**：`constraints` 必须是结构化对象（`{type: 'time_window', value: '02:00-05:00'}`），由 Flow Engine 在调度时校验、由执行 Agent 在运行时遵守、由 Review 阶段验证。自由文本约束降级为"提示性约束"，标注为不可自动校验。

## 10. 埋点与指标

| 埋点 | 用途 |
| --- | --- |
| `decision_detail_viewed{risk, from}` | 什么样的决策会被深入查看 |
| `option_selected{is_recommended}` | **推荐方案采纳率——Agent 决策质量的核心指标** |
| `constraints_added{count, type}` | 约束使用频率与类型分布 |
| `evidence_opened{type}` | 哪类证据真的被查看（未被查看的可以简化） |
| `similar_decisions_viewed` | 历史决策的参考价值 |
| `agent_mentioned_in_discussion` | @Agent 问答的使用率 |
| `decision_detail_duration` | 深度决策耗时（用于区分"卡片够用"与"必须详情页"的场景） |
| `revision_requested{reason_category}` | Agent 方案不足的类型分布 |

**页面成功标准**：推荐方案采纳率 60–85%（过低说明 Agent 方案差，过高可能说明人类在盲批）；约束附加率 > 30%（说明人类在真正参与而非简单放行）。

## 11. 边界与异常

| 情况 | 处理 |
| --- | --- |
| 方案超过 4 个 | 表格横向滚动；推荐方案固定在左侧不滚动 |
| 只有一个方案 | 不用对比表格，改为「方案说明 + 风险 + 影响」纵向布局，并说明为什么没有备选 |
| Agent 无明确推荐（置信度 < 60%） | 不标注"推荐"，改为「Agent 列出方案但无明确倾向，理由：…」 |
| 证据文件过大 | 内联预览前若干行 + 下载链接 |
| 讨论中 @Agent 但 Agent 不可用 | 提示「Agent 当前离线，将在恢复后回复」 |
| 决策已超时且关键路径已暂停 | 头部显示「关键路径已暂停 2h」，批准后自动恢复 |
| 批准的约束无法被系统执行 | 保存前校验，不可自动执行的约束标注「需人工确认遵守」并加入验收清单 |
| 会签人中有人离职 | 自动改派其上级，标注原因 |
| 同一决策被要求补充多次（> 2） | 提示「已重新分析 3 次，建议直接讨论或人工介入」 |
| 历史相似决策检索无结果 | 隐藏该区域，不显示空状态 |

## 12. 待确认问题

1. 结构化约束的类型体系需要定义（时间窗口、阈值中止、审批点、范围限制、通知要求…）。这是决定"约束能否被真正执行"的关键，建议 MVP 先定义 5–6 种最常用的。
2. 历史相似决策的检索方式：语义检索 vs 类型+标签匹配？前者效果好但成本高。MVP 建议用类型+资源+操作三元组匹配。
3. "结果如何"需要在决策执行后回填。回填由谁触发——自动关联执行结果，还是人工标注？倾向于自动关联为主（任务成功/失败/回滚），人工可补充。
4. 讨论区的 Agent 回答需要给 Agent 提供决策上下文，这会产生成本。是否需要限制每个决策的 @Agent 次数？
