# 12 · Localisation

> 中文：[12-i18n.md](12-i18n.md)

This document is about one thing: **the hands a human-readable sentence passes through between where it is produced and where it is shown**.

APOS copy comes from three places — written into the frontend, computed on the server, typed by the user — and the three are handled differently. Conflating them does not merely leave things untranslated; it fails *silently*: the Chinese UI looks fine, the English UI shows a wall of Chinese, and the person writing the code rarely switches languages.

---

## 1. Three kinds of copy

| Origin | Example | Belongs in | Test |
| --- | --- | --- | --- |
| The UI's own | Button labels, table headers, empty states | Message catalog | Words the platform wrote |
| Computed server-side | "This Agent is not a project member", "Rework rate 23%" | **Reason code + params** | Platform words, produced on the server |
| Typed by the user | Policy names, Agent names, requirement titles | Passed through verbatim | Words the user wrote |

**Never translate the user's words.** Translating a name the user chose is renaming it — they can no longer find the rule they created. These travel as `params` and land in a `{name}` slot in the catalog entry.

## 2. UI copy: the message catalogs

```
apps/web/src/lib/i18n/
  messages/
    buckets.ts        Which key prefix lives in which file — checked by structure.test.ts
    en/               English catalog, ten files by area
      common.ts       Shell, common actions, formatting, login
      errors.ts       Server-reported errors (one per ErrorReason)
      board.ts        Board and work items
      requirement.ts  Requirements and clarifications
      plan.ts         Plans and version diffs
      agent.ts        Agent config / detail / capabilities / access / runs
      analytics.ts    Analytics and overview
      policy.ts       Policies and decisions
      settings.ts     Roles / members / storage / integrations / notifications
      graph.ts        Execution graph, diagnostics, domain events
    zh/               Same shape; each module typed against its English counterpart
  en.ts               Merges the ten modules, exports en and MessageKey
  zh.ts               Same, and pins the whole as Record<keyof typeof en, string>
  index.ts            translate / useT / t / hasMessage
  locale.ts           Language selection and persistence
  spec.ts             useSpecText — reads bilingual fields off runtime specs
```

**Split by area, flat inside.** Splitting does not change the shape of a key: `t('board.empty')` is still one grep away. The file a key lives in is an organisational fact, not part of its name — nest them into `board.empty` object paths and grep stops working, and grep is the only way anyone finds where a string is used.

**Why split at all.** The previous shape was one 2,900-line file, with two costs. Every branch that touched copy conflicted at the bottom of the same file. And its section headers had drifted into names like "addendum two" and "the last batch" — named after *when* they were added rather than what they hold. That is not laziness; it is what necessarily happens when the only place to put a new key is the end.

**Why type per module.** Pinning only at the merge point means a missing Chinese key points at the whole 2,600-entry object — you get to find the missing one yourself. With `messages/zh/board.ts` typed against `messages/en/board.ts`, the error names the file and the key.

Three hard constraints:

**① English is the default.** The opposite trade-off from the theme: dark mode is on by default because it is about staring at a screen for hours; English is the default because someone who cannot read Chinese **cannot read the language switcher either**. Default to Chinese and an English speaker opens the app to a screen of characters — including the dropdown that would rescue them. Deadlock. Defaulting to English, a Chinese speaker can at least recognise 「中文」.

No browser language sniffing. `navigator.language` is frequently `zh-CN` on machines whose owners want the English UI (for screenshots, bug reports, external colleagues). Sniffing produces "I chose English, and on another machine it went back to Chinese".

**② The English side is the single source of truth for keys.** The Chinese side is typed `Record<keyof typeof en, string>`, and pinned **twice**: each `messages/zh/<area>.ts` against the English module of the same name, and the merged `zh.ts` against the whole. The first makes errors name a file and a key; the second catches anything a module missed. Adding a key on the English side without a Chinese counterpart is a **compile error**, not an English string surfacing in the Chinese UI after release.

The reverse — a key only on the Chinese side — is invisible to the type system, so `i18n.test.ts` asserts the two key sets match exactly.

**③ Never assemble a sentence from fragments.** Word order differs, so `{'共 '}{n}{' 条'}` can only be right in the language it was written in. The whole sentence is one entry; variables go in `{name}` placeholders.

A quick way to tell whether a piece of code is assembling: swap the variable for an English value and see whether the remaining fragments form an English sentence in place. If not, it is assembling.

### 2.1 Missing keys and missing params: ugly, but visible

| Case | Behaviour | Why |
| --- | --- | --- |
| Key does not exist | Return **the key itself**, warn in dev | An empty string means one missing sentence that nobody notices — and it may be the one explaining why a button is greyed out |
| Placeholder has no matching param | Leave `{count}` as-is | A blank merely reads awkwardly; `{count}` is obviously a bug — which is exactly how we want it read |

This is one instance of the failure mode this repository keeps paying for: **configuration that did not take effect, with no trace at the scene**.

### 2.2 Plurals

`{count} tasks are marked` is wrong at `count = 1` in English, while Chinese does not inflect for number. So "interpolate a count into a sentence written in the plural" looks permanently correct in the Chinese UI and is permanently wrong in the English one.

The convention: entries that need it supply `<key>_one` / `<key>_other`. Both are declared on the English side, so forgetting one is a compile error. The two Chinese variants are the same sentence — not redundancy, but the thing that stops a new English variant from silently skipping the Chinese side.

### 2.3 Module-level constants hold keys, not translations

```ts
const TABS: Record<string, MessageKey> = { flow: 'analytics.tab.flow' };  // ✅
const TABS: Record<string, string> = { flow: t('analytics.tab.flow') };   // ❌
```

Module-level constants cannot reach a hook, and they are not recomputed when the language changes — the translated string freezes in whichever language rendered first.

## 3. Server-produced copy: reason codes

### 3.1 Why prose alone is not enough

A Chinese sentence assembled on the server has two consumers: the Chinese UI and the English UI. It serves only the first. The English UI has two options — render it as-is (English users see Chinese), or pattern-match and rewrite it (matching prose that is free to change is a time bomb).

The test is **how many consumers the sentence has**: if it serves two of {Chinese UI, English UI, an action button such as "fix this" or "grant access"}, it has to be a code.

### 3.2 Shape

The server gives the code **and** the prose:

```ts
throw fail('VALIDATION_FAILED', 'storage.delivery_target_readonly', `交货目标 ${ref} 登记为只读…`, {
  params: { ref },
});
```

- `reason` — the UI resolves `error.reason.<reason>` from it
- `params` — fills the entry's placeholders; the user's own words pass through untranslated
- `message` — the Chinese sentence, for logs, alerts, and clients that do not know the code

**The UI reads the code, the log reads the sentence.** A code alone makes on-call staff look up a table at 3am; prose alone leaves the English UI with no option. Supplying both costs one field.

### 3.3 Reason codes across the system

| Code | Defined in | Surfaces at |
| --- | --- | --- |
| `ErrorReason` | `contracts/common/error-reason.ts` | Every HTTP error |
| `NotFoundEntity` | as above | `params.entity` on a 404 |
| `RejectionCode` / `RejectionScope` | `contracts/work-item/blocked.ts` | `work_items.blocked_detail`, executor picker |
| `DecisionReason` | `contracts/work-item/decision-reason.ts` | `decisions.reason_detail` |
| `Insight.code` | `domain/analytics/insights.ts` | Insights on the analytics page |
| `Contribution.key` | `domain/analytics/health.ts` | Health and delay-risk breakdowns |
| `PolicyIssue.type` | `domain/policy/audit.ts` | Policy audit findings |
| `CredentialProblemCode` | `api/modules/security/secrets.ts` | Agent / repository / storage-target health |

### 3.4 Why "not found" gets its own mechanism

`${what}不存在` cannot be assembled: the noun leads in Chinese and `not found` trails in English. A sentence built from pieces is only right in the language it was written in — the English side would produce `Artifactnot found`.

So the whole sentence is one entry per entity, and the entity name is **part of the key**: `error.notFound.project`. `notFound()` therefore takes an entity key (`'project'`), not prose.

### 3.5 One code, one sentence

This is the premise that lets a code serve as a catalog key. Two things break it:

- **One type covering several sentences.** Under `Insight.type`, `improvement` covers five entirely different sentences (flow efficiency / lead time / cost per delivery / automation rate / good-in-absolute-terms). Hence the finer `Insight.code`; `type` now only drives the icon and the ordering.
- **The same code meaning different things in two places.** Both health and delay-risk have `blocked`, but one explains points lost and the other explains why the date slips. The caller supplies the namespace: `analytics.health.blocked` / `analytics.delay.blocked`.

A ternary picking the sentence is the same problem in disguise:

```ts
fail('VALIDATION_FAILED', 'work_item.bad', a ? 'The executor is a person…' : 'No Agent set…')  // ❌
throw a ? fail(..., 'work_item.human_executor', ...) : fail(..., 'work_item.no_agent_specified', ...)  // ✅
```

### 3.6 Params carry language-neutral values

```ts
params: { range: '近 7 天' }   // ❌ the English sentence becomes "over the 近 7 天"
params: { days: 7 }            // ✅ the entry says "last {days} days" / "近 {days} 天"
```

Likewise, send `deploy` rather than "Deploy or release", `workspace.write` rather than "Edit workspace files" — the UI has entries for those enums.

Values already formatted into a language-neutral shape can travel directly: `34%`, `22h`, `1.2M`.

### 3.7 Lists are not joined on the server

```ts
params: { items: names.join('、') }   // ❌ 、 is the Chinese enumeration comma
```

English uses `, ` and wants `and` before the last item. Joining the list server-side hard-codes the conjunction into Chinese. Send the array; the UI joins with `joinList()`.

## 4. Enum copy belongs to the UI

Work item types, failure classifications, decision types, policy facts / operations / environments, runtime capabilities — these are **codes**, not copy.

```ts
import { FACT_LABELS } from '@apos/domain';      // ❌ that is a Chinese table
import { policyFactLabel } from '@/lib/format';  // ✅ catalog, falling back to the code
```

Importing a Chinese table into the frontend hard-codes the server's language into the UI — switching languages cannot undo it. The `XXX_LABELS` tables in domain remain, for server-side log lines.

The UI-side lookups live together in `apps/web/src/lib/format/index.ts` and share one shape: look up `<prefix>.<code>`, fall back to the code itself. Falling back to the code rather than a blank keeps a newly added enum value **visible**.

## 5. Gaps left on purpose

Not all Chinese should be translated. Two places deliberately keep the server's own sentence:

- `guard.failed` — carries the itemised list of which preconditions failed
- `policy.denied` — carries what that particular rule says

Replacing either with a generic translation ("a precondition is not met") leaves the user knowing neither which one nor what to do next. **Information matters more than language: a specific Chinese sentence beats a correct but useless English one.**

The list lives in `REASONS_WITHOUT_CATALOG` in `apps/web/src/lib/api/errors.ts`, each entry with its reason. It exists to separate "deliberately untranslated" from "forgotten" — the test reads this list, and without it the two would be indistinguishable.

The real fix is giving each reason in `domain/flow/guards.ts` its own code.

---

## 6. The tests that hold the line

| Test | What it guards |
| --- | --- |
| `i18n.test.ts` | The two catalogs have identical keys; no blank entries; placeholders match across languages |
| `errors.test.ts` | Every `ErrorReason` has an entry (unless exempted); no orphan entries; an unknown code falls back to prose rather than a blank |
| `no-literals.test.ts` | No Chinese literals in UI code (exceptions must state a reason) |
| `messages/structure.test.ts` | Keys live in the module their prefix belongs to; both languages group identically; no stale prefixes in the mapping |

All four watch for **silent failure**: breaking any of them is invisible in the Chinese UI.

`structure.test.ts` guards the organisation itself. Splitting into ten files fixed one 2,900-line file; it does not stop a new key from landing in the wrong module — and misplacement accumulates. A year later half the analytics entries sit in `common.ts`, "organised by area" is true only on paper, and the mess is now spread across ten files instead of one. The failure message says where the key is and where it belongs, so it can be acted on directly.

`no-literals.test.ts` checks Chinese only. No single regex separates hard-coded English copy from class names, enum values and URLs — and a rule that cries wolf does not survive three commits before somebody disables it, at which point it stops checking Chinese too.

## 7. Adding a sentence

**UI copy** → find the module its prefix belongs to, add the key to `messages/en/<area>.ts` and the counterpart to the same file under `messages/zh/` (skipping it is a compile error). A new prefix has to be registered in `messages/buckets.ts`, or `structure.test.ts` fails.

**A server error** →

1. Add the code to `ErrorReason`
2. Throw with `fail(code, reason, chineseProse, { params })`
3. Add `error.reason.<code>` to both catalogs
4. Put variables in `params`, as language-neutral values

**Other server-produced copy** (metrics, insights, diagnostics) → give it a `code`/`key` plus `params`, keep the Chinese as the fallback, and let the UI resolve from the code.

**Enum copy** → add catalog entries and an `xxxLabel()` in `format/index.ts`; do not import a Chinese table from domain.
