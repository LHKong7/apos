# 12 · 多语言

*[English version / 英文版本](12-i18n.md)*

> 这篇写的是现在的样子，它止步于浏览器。[13 · 前后端统一多语言](13-i18n-unified.zh.md) 把同一套纪律推到所有从别的门离开产品的路径上 —— 通知、导出、日志 —— 并补掉 §5 的缺口。


这篇讲一件事：**一句给人看的话，从产生到显示，要经过哪些手**。

APOS 的文案有三个来源 —— 前端写死的、服务端算出来的、用户自己填的 —— 三者的处理方式完全不同。混为一谈的代价不是「翻译不全」，而是**沉默失效**：中文界面上一切正常，英文界面上露出一片中文，而写代码的人通常不切语言。

---

## 1. 三类文案

| 来源 | 例子 | 归属 | 判据 |
| --- | --- | --- | --- |
| 界面自己的 | 按钮名、表头、空态提示 | 词条表 | 平台写的词 |
| 服务端算出来的 | 「这个 Agent 不是项目成员」「返工率 23%」 | **原因码 + 参数** | 平台写的词，但产生在服务端 |
| 用户填的 | Policy 名、Agent 名、需求标题 | 原样透传 | 用户写的词 |

**用户写的词不翻译**。把用户起的名「翻译」一遍等于给它改名 —— 他在界面上再也找不到自己建的那条规则。这类词一律作为 `params` 原样带过去，落在词条的 `{name}` 槽里。

## 2. 界面文案：词条表

```
apps/web/src/lib/i18n/
  messages/
    buckets.ts        哪个前缀住在哪个文件 —— 由 structure.test.ts 核对
    en/               英文词条，按区域分十个文件
      common.ts       全局外壳、通用动作、格式化、登录
      errors.ts       服务端报错（与 ErrorReason 一一对应）
      board.ts        看板与工作项
      requirement.ts  需求与澄清
      plan.ts         计划与版本对比
      agent.ts        Agent 配置 / 详情 / 能力 / 授权 / Run
      analytics.ts    分析页与总览
      policy.ts       Policy 与决策
      settings.ts     角色 / 成员 / 存储 / 集成 / 通知
      graph.ts        执行图、诊断、领域事件
    zh/               同构；每个模块各自钉在英文对应模块上
  en.ts               合并十个模块，导出 en 与 MessageKey
  zh.ts               同上；整表再钉一次 Record<keyof typeof en, string>
  index.ts            translate / useT / t / hasMessage
  locale.ts           语言选择与持久化
  spec.ts             useSpecText —— 读运行时规格上的双语字段
```

**按区域分文件，文件内仍是扁平的。** 拆分不改变键的形态：`t('board.empty')` 照样一搜就到。键住在哪个文件是组织方式，不是它名字的一部分 —— 一旦嵌套成 `board.empty` 那样的对象路径，grep 就失效了，而 grep 是唯一能查清一句话用在哪儿的办法。

**为什么要拆。** 此前是一个 2900 行的单文件，代价有两处：改文案的分支全在同一个文件尾部冲突；而它的分节名已经漂成「补遗二」「最后一批」这种 —— 按**加入时间**命名而不是按内容。那不是谁偷懒，而是「新键只能往末尾加」的必然结果。

**为什么逐模块钉类型。** 只在合并处钉一次的话，中文少一个键的报错会指着整张 2600 条的表 —— 少了哪一条得自己找。`messages/zh/board.ts` 钉在 `messages/en/board.ts` 上之后，报错直接指到文件和键名。

三条硬约束：

**① 英文是默认语言。** 与主题相反的取舍：深色主题默认开，因为它关乎长时间盯屏；语言默认英文，因为不认识中文的人**看不出切换器写着什么**。默认中文的话，英文用户打开界面看到一屏方块字，而那个能救他的下拉框也是方块字 —— 死锁。默认英文时，中文用户至少认得「中文」两个字。

不做浏览器语言嗅探。`navigator.language` 在国内环境下经常是 `zh-CN` 而使用者其实要英文界面（截图、报 bug、给外部同事看）。嗅探的结果是「我明明选了英文，换台机器又变回中文」。

**② 英文侧是键的唯一真相来源。** 中文侧的类型是 `Record<keyof typeof en, string>`，而且**钉两次**：每个 `messages/zh/<区域>.ts` 钉在同名的英文模块上，合并后的 `zh.ts` 再钉一次整表。前者让报错指到具体文件与键名，后者兜住模块本身漏掉的情况。在英文侧加了键而中文没补，是**编译错误**，不是上线后中文界面上突然冒出一句英文。

反过来，中文侧多出一个英文侧没有的键，类型系统管不了 —— 由 `i18n.test.ts` 断言两张表的键一一对应。

**③ 不许拼句子。** 两种语言语序不同，`{'共 '}{n}{' 条'}` 这种写法只在中文里成立。整句是一条词条，变量走 `{name}` 占位符。

判断一处「算不算拼句子」的办法：把中间那段变量换成英文，看剩下的部分能不能原地组成一句英文。不能，就是拼了。

### 2.1 缺键与缺参数：要丑，但要看得见

| 情况 | 行为 | 为什么 |
| --- | --- | --- |
| 键不存在 | 返回**键本身**，dev 下 warn | 返回空串的话，界面上少一句话没人会注意到 —— 而它可能正是解释「为什么这个按钮是灰的」那句 |
| 占位符没有对应参数 | 保留 `{count}` 原样 | 空白只是让句子读起来别扭，`{count}` 明摆着是个 bug —— 而这正是我们希望它被当成的东西 |

这是整个仓库反复吃的那个亏的一个实例：**配置没生效而现场毫无迹象**。

### 2.2 单复数

英文里 `{count} tasks are marked` 在 `count=1` 时是错的，中文「{count} 个任务」不分单复数 —— 于是「把 count 插进一句写死复数的话」在中文界面上永远看起来是对的，英文界面上永远是错的。

约定：需要区分的词条额外提供 `<key>_one` / `<key>_other`。两条都在英文侧声明，所以漏写是编译错误。中文两条写成同一句话，这不是冗余 —— 它保证加英文变体时不会忘了中文侧。

### 2.3 模块级常量存键，不存译文

```ts
const TABS: Record<string, MessageKey> = { flow: 'analytics.tab.flow' };  // ✅
const TABS: Record<string, string> = { flow: t('analytics.tab.flow') };   // ❌
```

模块级常量取不到 hook，而且切语言时不会重算 —— 译好的字符串会停在第一次渲染时的那个语言。

## 3. 服务端文案：原因码

### 3.1 为什么不能只给一句话

一句服务端拼好的中文有两个消费者：中文界面和英文界面。它只服务第一种。英文界面拿到它只有两条路 —— 原样显示（英文用户看到中文），或者反过来正则匹配它再改写（匹配一句随时会改的话是定时炸弹）。

判据是「**这句话有几个消费者**」：只要中文界面、英文界面、和某个按钮（「一键修复」「去授权」）三者中占了两个，就必须是码。

### 3.2 形态

服务端**同时**给码和句子：

```ts
throw fail('VALIDATION_FAILED', 'storage.delivery_target_readonly', `交货目标 ${ref} 登记为只读…`, {
  params: { ref },
});
```

- `reason` —— 界面按它取 `error.reason.<reason>` 那条词条
- `params` —— 填进词条的占位符；用户写的词原样带
- `message` —— 中文句子，喂日志、告警、和认不出码的老客户端

**界面读码，日志读句子。** 只给码的话，值班的人半夜看日志要多查一张表；只给句子的话，英文界面没救。两个都给的成本只是一个字段。

### 3.3 全站的原因码

| 码 | 定义在 | 落在哪 |
| --- | --- | --- |
| `ErrorReason` | `contracts/common/error-reason.ts` | 所有 HTTP 报错 |
| `NotFoundEntity` | 同上 | 404 的 `params.entity` |
| `RejectionCode` / `RejectionScope` | `contracts/work-item/blocked.ts` | `work_items.blocked_detail`、执行者下拉框 |
| `DecisionReason` | `contracts/work-item/decision-reason.ts` | `decisions.reason_detail` |
| `Insight.code` | `domain/analytics/insights.ts` | 分析页的系统发现 |
| `Contribution.key` | `domain/analytics/health.ts` | 健康度 / 延期预测的逐项拆解 |
| `PolicyIssue.type` | `domain/policy/audit.ts` | Policy 体检结论 |
| `CredentialProblemCode` | `api/modules/security/secrets.ts` | Agent / 仓库 / 存储目标的健康度 |

### 3.4 「找不到」为什么单列

不能拼 `${what}不存在`：中文里名词在前，英文里 `not found` 在后。拼出来的句子只在写它的那种语言里成立 —— 英文侧会得到 `Artifactnot found` 这种东西。

所以整句是一条词条，实体名是**键的一部分**：`error.notFound.project`。`notFound()` 的实参因此是实体键（`'project'`）而不是中文。

### 3.5 一个码对应一句话

这是码能当词条键用的前提。两处容易破坏它：

- **一个 type 底下多句话**。`Insight.type` 里 `improvement` 一个类型有五句完全不同的话（流动效率 / 前置时间 / 单位用量 / 自动化率 / 绝对值够好）—— 所以另立了更细的 `Insight.code`，`type` 只用来决定图标与排序。
- **同名码在两处说不同的话**。健康度和延期预测都有 `blocked`，但一个说「扣了多少分」，另一个说「为什么会晚」。解法是命名空间由调用方给：`analytics.health.blocked` / `analytics.delay.blocked`。

三元表达式挑句子是同一个问题的伪装形态：

```ts
fail('VALIDATION_FAILED', 'work_item.bad', a ? '这张卡的执行者是人…' : '还没指定执行 Agent…')  // ❌
throw a ? fail(..., 'work_item.human_executor', ...) : fail(..., 'work_item.no_agent_specified', ...)  // ✅
```

### 3.6 参数一律送语言中立的值

```ts
params: { range: '近 7 天' }   // ❌ 英文句子会变成 "over the 近 7 天"
params: { days: 7 }            // ✅ 词条自己说 "last {days} days" / "近 {days} 天"
```

同理，操作类型送 `deploy` 而不是「部署发布」，能力送 `workspace.write` 而不是「修改工作区文件」—— 界面自己有那些枚举的词条。

已经格式化成语言中立形态的值可以直接送：`34%`、`22h`、`1.2M`。

### 3.7 列表不在服务端拼

```ts
params: { items: names.join('、') }   // ❌ 「、」是中文的顿号
```

英文用 `, ` 且最后一项前要有 `and`。服务端拼这个列表，等于把连接词也硬编成中文。送数组，界面用 `joinList()` 拼。

## 4. 枚举的说法归界面

任务类型、错误分类、决策类型、Policy 的 fact / 操作 / 环境、运行时能力项 —— 这些都是**码**，不是文案。

```ts
import { FACT_LABELS } from '@apos/domain';   // ❌ 那是一张中文表
import { policyFactLabel } from '@/lib/format';  // ✅ 词条 + 回落到码本身
```

前端 `import` 一张中文表，等于把服务端的语言硬编进界面 —— 切了语言也换不掉。domain 里那些 `XXX_LABELS` 留给服务端拼日志。

界面侧的取词函数集中在 `apps/web/src/lib/format/index.ts`，形态一致：查 `<前缀>.<码>`，取不到就回落到码本身。回落到码而不是空白，是为了让新增的枚举值**看得见**。

---

## 5. 有意留着的缺口

不是所有中文都该翻。有两处**故意**保留服务端原句：

- `guard.failed` —— 带的是「哪几条前置条件没过」的逐条说明
- `policy.denied` —— 带的是那条规则自己的说法

换成一句通用译文（「有条件没满足」），用户就不知道是哪一条、也不知道下一步做什么。**信息量比语言更重要：一句具体的中文，好过一句正确但没用的英文。**

这份名单写在 `apps/web/src/lib/api/errors.ts` 的 `REASONS_WITHOUT_CATALOG` 里，每条附理由。它存在的意义是把「故意没翻」和「忘了翻」分开 —— 测试认这份名单，没有它两者在测试里长得一模一样。

要真正修好，得让 `domain/flow/guards.ts` 那几条理由各自带码。

## 6. 守门的测试

| 测试 | 守什么 |
| --- | --- |
| `i18n.test.ts` | 两张表的键一一对应；没有空词条；占位符在两种语言里一致 |
| `errors.test.ts` | 每个 `ErrorReason` 都有词条（除非在豁免名单里）；没有孤儿词条；认不出的码回落到原句而不是空白 |
| `no-literals.test.ts` | 界面代码里没有中文字面量（例外要写明理由） |
| `messages/structure.test.ts` | 键住在它前缀该住的文件里；中英两侧同构；归属表里没有过期前缀 |

这四条都盯着**沉默失效**：破坏它们在中文界面上看不出任何问题。

`structure.test.ts` 守的是组织方式本身。拆成十个文件解决的是「单文件 2900 行」，解决不了「新键放错文件」—— 而放错是会累积的：一年后 `common.ts` 里躺着一半的 analytics 词条，「按区域分文件」就名存实亡了，只不过这次分散在十个文件里，比原来更难看清。它报的是「这条键在哪儿、该去哪儿」，可以直接照着搬。

`no-literals.test.ts` 只查中文，不查英文 —— 没法用一条正则把「写死的英文文案」和「类名、枚举值、URL」分开，而一条会误报的规则活不过三次提交，最后一定是被 disable 掉，那时它连中文都不查了。

## 7. 加一句话的时候

**界面自己的文案** → 按前缀找到对应的 `messages/en/<区域>.ts` 加键，`messages/zh/` 同名文件补上（不补是编译错误）。新前缀要登记进 `messages/buckets.ts`，否则 `structure.test.ts` 会红。

**服务端的报错** →

1. `ErrorReason` 加码
2. 抛错处 `fail(code, reason, 中文句子, { params })`
3. 两张词条表加 `error.reason.<码>`
4. 变量走 `params`，语言中立的值

**服务端的其他文案**（指标、发现、诊断）→ 让它带 `code`/`key` + `params`，中文留作兜底，界面按码取词。

**枚举的说法** → 词条 + `format/index.ts` 里加一个 `xxxLabel()`，别在前端 import domain 的中文表。
